The trap is that a delta without versioning is a time bomb. You never detect that you missed something, and your screen silently diverges from reality. Always have a resynchronization strategy, and that's exactly what the last-event-ID mechanism makes easy.

Then there's reconciliation with the cache, which I'd argue is the real frontend subject of real time.

An incoming event must not overwrite an in-flight optimistic mutation. If I've just clicked book and my interface already shows the spot as mine, a server event saying there are three spots left must not put it back. Reconciliation has to know about mutations in progress.

On reconnect, resynchronize the visible state rather than replaying a potentially long history.

Batch the updates. If two hundred seats change in one second, we don't apply two hundred re-renders, we aggregate over an animation frame.

And subscribe only to what's visible, unsubscribing when the tab is hidden, with a resync on return. That's a mobile reflex, battery and connection budget, and it matters in the conditions our users are actually in.

[long pause] If you want a component to go deep on, I'd propose the seat selector, because it concentrates every hard problem in this design into one place.

It's the choose your spot component. On some classes, spinning with numbered bikes, reformer pilates, you don't book an abstract spot, you book a specific one on a floor plan. It's also the only component here that genuinely justifies a WebSocket.

The most important design point is that it has three layers of state with three different lifetimes, and that follows directly from availability being a projection.

The floor plan is server data, near static, cacheable for hours. It only changes if the room is rearranged. The seat states for this session are volatile, real-time, never persisted. And my current selection is purely local UI state that has no meaning outside the flow.

[medium pause] Two separate resources with two different cache lifetimes. If I merge them into one payload, I re-download the entire room layout on every availability update, which is pure waste on a channel that fires several times a second.

On concurrency, we place an optimistic hold on the seat that was clicked so the feedback is instant, but it's only guaranteed once the server validates. If someone took it in between, we roll back and say pick another seat. It's the same logic as double booking, applied at a finer granularity.

Three details make the difference here.

The conflict experience. The just taken state should be animated, not abrupt. A seat that vanishes bluntly while you're aiming at it is disorienting. A smooth transition communicates what's happening. It's a small thing, but it's the kind of small thing that distinguishes someone who has built interfaces from someone who has specified them.

Reconciliation. A seat twelve is taken event must never wipe out the rest of my current selection. The server owns the seats, the client owns my selection. If the conflict is genuinely on a seat I had selected, the server wins and the seat goes, but it goes explicitly, with an explanation, never silently.

And accessibility, which I'd raise here without being asked, because this is the hardest thing in the whole application to make accessible. A visual grid of clickable boxes gives a screen reader nothing. You need keyboard selection, with labels that carry both the spatial information and the state, something like bike twelve, available, front row. And you need to announce changes without drowning the user in constant voice notifications.
