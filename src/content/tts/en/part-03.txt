Below that, local UI state. Filters, whether a modal is open, the hovered seat, the current step in the flow, scroll position.

Below that, server state and cache. Sessions, availability, my profile, my bookings.

Below that, transport. The HTTP client, the real-time channel, the offline queue.

And underneath everything, cross-cutting services. Authentication, internationalization, tenant theming, feature flags, telemetry.

The principle is that each layer has a single responsibility, and the lower layers know nothing about the upper ones. The HTTP client doesn't know that a class card component exists. The cache doesn't know how we render an error.

I want to connect that to clean architecture, since you mentioned it. Clean architecture isn't a backend-only idea. Its central proposition, the domain at the centre, independent of infrastructure, with dependencies pointing inward, applies perfectly on the client.

[medium pause] The domain logic, what a booking is, what states it can be in, what makes a session bookable, shouldn't know whether data arrives over REST, GraphQL or a WebSocket. If I keep that separation, I can swap the transport, test the domain without a network, and share that layer with the mobile app. That's dependency inversion applied to the client.

And that has a practical consequence worth stating. It's what makes web and mobile code sharing possible and sensible. The domain layer, the rules, the state machine, the types, is pure TypeScript and shares completely. The presentation layer doesn't share well, and shouldn't. So the trade-off I'd defend is: share what's invariant, specialize what's contextual.

Now let me tell you the path of a booking through those layers, because data flow is more useful here than a box diagram.

[medium pause] The user clicks. The component doesn't call the API. It dispatches a mutation. The mutation layer generates an idempotency key, applies an optimistic update to the cached session so the interface reflects the change immediately, and fires the request. On success it writes the response into the cache and invalidates the related keys. On a business failure it rolls back to the snapshot and surfaces a typed reason that the component maps to a specific interface. On a network failure it retries with the same key. Meanwhile the real-time channel may push an update for that same session, and the reconciliation logic has to apply it without clobbering the in-flight optimistic change.

On the component breakdown, here's how I'd cut it.

The schedule page is the container. Orchestration, high-level fetching, routing. The filters component owns date, discipline, studio and instructor. It's a container, with local state mirrored into the URL. The schedule list renders the list, and virtualizes only if we decided we need it. It's presentational. The class card renders one slot and its business state, also presentational. The booking flow is the state machine for the journey. The seat selector handles seat selection and its own real-time channel. The waitlist button handles joining and showing position. And a membership badge shows credits and eligibility.

The container versus presentational distinction isn't cosmetic here, and I want to say why. The real benefit is stability. Presentational components don't change when the API changes. If the class card receives a well-defined props object rather than fetching its own data, reworking the API contract doesn't touch it. On a codebase that lives five years, that's the difference between a localized refactor and a project.
